# Taste
- Communicates casually and informally — terse, lowercase feature requests, bug reports, and one-word continuations ("fix it", "continue", etc.) in both English and Bahasa Indonesia (e.g., "buat agar ... jadi buatkan tombol ..."), rather than structured specs, often attaching screenshots to illustrate the issue. Confidence: 0.97
- Runs the project on Windows and prefers a single entry-point startup — requested a `start.bat` at the project root so the whole program (dashboard + WhatsApp bot) launches in one terminal with one command instead of managing separate processes. Confidence: 0.7
- Prefers operational actions (like resetting WhatsApp) to be available as buttons directly in the web UI, rather than requiring manual file/folder manipulation (e.g., manually deleting the `auth_info` folder to reset the session); expects these controls to be easy to reach from the dashboard main page and the navbar, and reports it as a bug when they are missing after a restart. Confidence: 0.88
- Expects the WhatsApp bot session to persist and resume automatically across program restarts — after stopping and re-running the program, the bot should keep responding to incoming chats without any manual re-setup or re-scan. Confidence: 0.7
- Prefers a diagnose-first workflow: when reporting a bug, explicitly asks the assistant to find/investigate the root cause before making any fixes ("cari tau masalahnya terlebih dahulu, baru selesaikan masalahnya"). Confidence: 0.9
- Prefers WhatsApp bot confirmation messages to be visually prominent and eye-catching — an ALL-CAPS bold title wrapped in decorative emojis (✨ *✅ PERMINTAAN ANDA TELAH DITERIMA!* ✨) with per-line emojis (🎉👤📝⏳💡), rather than plain single-paragraph text. Confidence: 0.7
- Prefers browser/OS notifications to be concise and action-directed — just tell the admin to open WhatsApp to respond (e.g., "Ada yang ingin bicara langsung! … Buka WhatsApp untuk merespons"), not verbose event descriptions or feature codes. Confidence: 0.75
- Reversed course on dashboard live-chat notifications: after initially asking to restyle the browser/banner notifications, later asked to delete them entirely from the dashboard ("untuk notif di dashboard hapus saja") — prefers a clean dashboard with no notification banners/pop-ups or OS notifications, and expects the now-unused notification script/files to be removed rather than left as dead code. Confidence: 0.8
- Prefers UI consistency across admin pages: the navbar menu must be identical on every dashboard page (same set of items as the main dashboard), and flags pages with fewer/different menu items as needing to be brought in line ("untuk navbar samakan semua seperti di dashboard"). Confidence: 0.85
- Prefers sessions to end silently for the end user: when a live chat session ends (admin `!selesai`, auto-expiry, or stale session), no "session ended" message should be sent to the WhatsApp user — the session is still closed server-side and the admin still gets notified. Confidence: 0.8
- Uses `git reset` to undo the last commit when assistant work introduces regressions, and expects the assistant to diagnose git history (compare HEAD vs working copy, check backups) and restore the lost feature set rather than rebuilding from scratch. Confidence: 0.7
- Expects all content management (assigning services to categories, adding sub-options each with their own requirement lists) to be editable from the dashboard admin forms, not just wired in the bot — a "restored feature" must include its management UI. Confidence: 0.7
